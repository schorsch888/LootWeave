# Runtime experiment protocol

Declared on 2026-10-05 before collecting control cohorts. This is a development comparison, not M4 cold-start, visible-GUI or clean-machine acceptance. The [performance plan](performance-plan.md) defines the unchanged release gates.

Use [benchmark_runtime.py](../scripts/benchmark_runtime.py) on one Windows builder with the same Python executable, synthetic BMP, demo fixture, knowledge-pack bytes and OS cache condition. Keep game inputs, screenshots, captures, personal paths and credentials out of public results. Raw reports and isolated state remain under ignored `.local/runtime-benchmark`; review sanitized summaries before publication.

Run order is control A, control B, then candidate, with at least 20 fresh-state launches in each cohort. The control is the unchanged eager development launcher source snapshot `eade0dc`; export it locally with `git archive` and build its locked frontend independently. Candidate source/artifact identities must be recorded. No builds, browser tests or domain suites run concurrently with a cohort; document interruptions and retain failed attempts. OS caches remain warm: a fresh process/state directory is not a cold-cache procedure.

The primary latency metric is launch-to-complete synthetic manual confirmation/evaluation P95, using nearest rank and every recorded attempt. Separately report shell/Gateway readiness, usable core, manual request work, catalog response, frozen replay, optional activation, first and repeated OCR, first Planning and shutdown. A faster shell alone is insufficient. Phase timings are process-local durations or owner-relative durations, never differences between unrelated clocks.

The predeclared comparison rule is candidate primary P95 below the faster control P95 by more than the absolute difference between the two control P95s. Core-only idle private commit must fall by more than the absolute difference between the two control maxima. These are conservative development comparisons with only two control cohorts, not confidence intervals or guarantees on other machines. If variability obscures the benefit, defer the policy or collect more evidence.

Allowed regressions: first-use OCR and Planning activation plus business request P95 must each remain at most three seconds on the disclosed synthetic input; shutdown P95 at most five seconds. Core correctness and frozen replay must remain identical, with zero startup/workflow/cleanup failures. After optional activation, maximum idle private commit must remain no greater than the larger control maximum plus the controls' absolute difference. Keep the existing M4 working-set budget unchanged; this headless comparison cannot establish total desktop memory acceptance.

For the first cycle of each cohort, sample 60 seconds at one-second intervals after the complete manual/replay flow, then another 60 seconds after OCR and Planning activation. Discover owned descendants every 100 ms; retain their process handles through exit, measure peak counters during work, and disclose missed short-lived helper risk. Sum working sets conservatively (shared pages may be counted repeatedly) and report private commit separately. Idle CPU is normalized to one logical processor. These windows characterize one stable state per cohort; they do not provide 20 independent idle-memory samples or WebView memory.

P3 selected-pack loading requires evidence that catalog initialization or retained data dominates this seven-pack workload. P5 persistent OCR initialization requires separately measured helper setup savings and an acceptable retained-memory/lifecycle cost; whole-request timing alone cannot attribute that cost. Retain current policies where these prerequisites are missing. Frontend splitting requires byte benefit and recoverable actual chunk failures, while mount-once secondary panels preserve drafts independently of code splitting.
