# Implementation reference

The implementation lives directly in the repository root. There is no enclosing application directory. The only executable pack is `synthetic-leveling` version `1.0.0`, scoped to the entirely fictional game ID `lootweave-fixture` and its Sorcerer leveling scenario. Deskrawl build 25690430 has research-only pack versions `0.1.0-research` through `0.7.0-research`; the latest adds a static Frostwyrm staff dependency path, `LegendaryStaff1` → `EquipmentEffect` resource 4793 → `SorcererBasicAttack2` (Ice Shards), while leaving `rules` empty and `mechanics_accepted=false`. Earlier `0.1.0`–`0.6.0` pack bytes and hashes remain unchanged, and all seven explicit versions are available through the API. The source association is research-only and does not establish online mechanics. Diablo II, III and IV do not have accepted adapters.

For installation, launch commands, checks, and troubleshooting, use the [development guide](development.md). Dated measurements and local artifact identities belong in the [validation record](validation.md); a source description does not establish release acceptance.

## Core workflow

The current source opens on a blank profile. Structured forms record uniquely identified owned items as candidates, equipped items, or unequipped inventory; SQLite preserves those records and their evidence across reopening. Future loadouts can reference only recorded owned items, and equipment use is checked against slot, class, level, and source requirements. Adding an item to inventory does not equip it automatically. Skills retain actor, rank, and effect data, while unconfirmed conditions continue to block conclusions.

Players can record evidence-linked material and currency balances. Engine 0.1.8 adds explicitly confirmed preparation options for equipment and six types: skill, talent, Paragon, rune, companion, and temporary effect. Options preserve before/result state, context/class, required level/rank/unlock state, costs or unknown costs, evidence, and unknowns. Future plans select option IDs, carry complete sources, gear, and conditions, and may set resource limits. The evaluator combines known costs for deficits and budget excess while preserving actual skill rank, actor, and effects. Preparation feasibility remains separate from game-mechanic outcomes, and projections do not change current equipment or its build hash. Unknown costs, unlocks, changed inputs, capture-time conflicts, random results, or missing supporting options stay unconfirmed. No real-game DPS calculation or retain/equip recommendation has passed acceptance.

## Boundaries

| Location | Ownership |
| --- | --- |
| frontend/src | React/TypeScript FSD: App assembles Pages, Pages compose Features and Entities, Shared provides transport and wire types |
| desktop/src | Rust/Tauri entry, Windows region capture, sessions, readiness, instance lock and descendant cleanup |
| services/profile | Unconfirmed observations and append-only confirmed snapshots; owns profile.sqlite3 |
| services/knowledge | Immutable, scoped packs and evidence; owns the pack index and content hashes |
| services/evaluation | Full-build mechanism comparison, reasons and frozen replay; owns evaluation.sqlite3 |
| services/planning | Comparable XP/time trials, source prerequisites and recorded-outcome statistics; owns planning.sqlite3 |
| services/ocr | Native Windows OCR infrastructure; owns private captures, never confirms Profile data |
| gateway.py | Authenticated UI forwarding and static assets; no game rules |
| contracts.py, transport.py, storage.py, process_lifecycle.py | Wire validation, local HTTP, SQLite and service-process lifetimes; no shared business model |

Capabilities run in separate processes and communicate through versioned HTTP APIs. Evaluation reads Profile and Knowledge, and Planning reads Knowledge. Neither opens another capability's database. The architecture check rejects upward FSD imports, feature peers, private slice imports and cross-service Python imports.

Python service runtime dependencies are standard-library modules and installed Windows APIs. Release bundles embed CPython; React, Tauri and build tools use locked dependencies. Separately runnable services and independent data ownership form the microservice boundary, while the Windows distribution packages them together.

## Development

Follow the [source setup](development.md#run-the-experimental-source) and [Windows build instructions](development.md#build-the-windows-desktop). Native capture/OCR and desktop packaging require Windows x64.

The development launcher creates a session secret on an ephemeral literal-loopback address. Default `eager` starts all services sequentially before serving the shell. Explicit `--startup-policy on-demand` serves the shell before core readiness, starts Profile/Knowledge concurrently then Evaluation, and starts OCR/Planning on an explicit capability request. Its [measured experiment](performance-results.md) passed correctness and memory checks but failed the primary startup-tail comparison, so default promotion is deferred. Each service requires authenticated readiness. Data defaults to ignored `.local`; Ctrl+C stops workers. Rust owns the desktop outer process scope. Before initialization, each Windows service retains an anonymous, non-inherited kill-on-close [job object](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) for its lifetime; Windows reclaims owned helpers on service exit or forced termination.

For desktop service launches, Rust assigns its outer job before writing a one-byte boot permit to the service's existing stdin pipe. With `LOOTWEAVE_PARENT_JOB=1`, Python waits for that permit before establishing the nested service job or initializing helpers. Missing/invalid permits and ownership failures publish no readiness. The developer launcher clears the inherited desktop flag and starts independent service roots. Process cleanup is scoped to owned descendants; unrelated siblings remain running. The frozen sidecar and current Rust host must be rebuilt together before validating this protocol in a packaged application.

Build products are local and ignored. The development guide documents build options and external prerequisites; an installer build does not complete clean-machine acceptance.

### OCR behavior

English en-US and Simplified Chinese zh-Hans-CN OCR models are installed Windows capabilities. Text confirmation remains usable when a model or capture is unavailable. The current OCR adapter supports three generic demonstration labels: level, vitality and armor. It does not identify arbitrary affixes, icons or game layouts. Numeric parsing rejects split or incomplete digits and scientific-notation fragments, and preserves the original text, sign and unit. A readable primary recognition remains the numeric source; consistent English recognition is recorded separately as `numeric_corroboration`. `numeric_source` is reserved for cases where an unreadable number was actually recovered. The original observation and every interpreted value remain unconfirmed until the user reviews and confirms them.

Unresolved fields with a unique mapped label, explicit unit and uncontested native row geometry can request English numeric-region recognition. The worker uses the original BMP and one additional helper for at most three crops, projects word bounds back to original pixels and retains the original text/span. Readable primary values and explicit signs are preserved; conflicting candidates remain ambiguous, and consistent crops corroborate rather than replace readable values. The helper has a six-second maximum within the remaining twelve-second request budget; failure is recorded as `numeric_region_error` while primary observations remain usable. Each crop bitmap and input stream is disposed, and the helper stays in the service process scope. All values still require confirmation. The frozen current adapter's fresh synthetic v7 measurement is documented below; real-game acceptance remains open.

Screenshot captures in the updated source are persisted first as unconfirmed observations. Recapture, OCR failure, and manual saving preserve the original screenshot reference; reviewed fields become snapshot facts only after human confirmation. Missing Windows OCR language models still allow manual text entry.

OCR review accepts or ignores each non-empty raw-text line and each parsed field not represented by a complete matching raw-text line, independently. Known and custom affixes require explicit value/unit review; `required_level` is confirmed separately. After all rows are handled, one apply action writes the reviewed fields to the candidate; a matching affix ID is replaced by the reviewed value on application. Screenshot evidence is attached only to mapped candidate fields while raw text, unrelated evidence sources, and capture time remain preserved. A new screenshot resets the review state. An independent UI gate matches the reviewed `observation_id`, so deleting a snapshot unknown marker cannot bypass review. Percent values retain their original unit, and duplicate targets prevent application. The OCR model and parsing algorithm remain unchanged; engine 0.1.8 adds the preparation-option group.

## Deskrawl process and window capture

The current source includes passive Deskrawl process/window detection in the Rust host. With game scope `deskrawl`, the capture feature requires explicit window selection, uses client-relative physical coordinates, and provides a three-second countdown to return manually to the game. Other scopes can retain explicit screen-region capture. The native commands are `detect_deskrawl_windows` and `capture_deskrawl_region`, each authorized by the launch session and application command permissions.

Detection reads only OS process/window metadata. It checks the executable basename and process creation identity. Minimized, hidden and unavailable windows cannot be selected; a background window can be selected, but capture requires manually bringing it to the foreground. The host verifies the same client bounds before and after the screen-region read. Multiple windows are not silently resolved. Redetection replaces session-scoped bindings. Responses are applied only when their detection generation and current context still match, so a late result cannot replace a newer window list after a scope or source change. Only game metadata is returned; full paths, PIDs, window handles and window titles are excluded. Game version and build remain unknown in the capture context.

GDI reads the selected foreground screen region inside the game client. It is not an atomic window-only capture API; overlays and changes between checks still require manual review. After capture, the UI displays the original BMP region at its native pixel dimensions and the uncorrected OCR text. The image viewer is keyboard-focusable and scrollable for larger regions. Changing game scope, capture source, selected window binding, region or language, or starting another capture clears the old image and observation association and invalidates confirmation while preserving manually entered text. Original image/text and window provenance remain unconfirmed until the separate Profile confirmation flow. A declared capture game must match the snapshot game; each new observation resets the manual checkbox.

The window source and simulated UI guards have recorded checks. The historical `fcc9ed1` MVP host, frozen Python and NSIS installer were built locally and passed the recorded headless lifecycle and backup/restore checks. Subsequent builds have separate identities in the [validation record](validation.md); results from distinct artifacts must not be combined. Successful real-window capture, visible GUI and two-clean-machine installation/removal remain unaccepted. Run the lightweight Windows checks independently of desktop resources:

~~~powershell
cargo fetch --locked --target x86_64-pc-windows-msvc --manifest-path desktop/Cargo.toml
python scripts/check_window_guards.py
~~~

Per user direction, named-owner/reviewer assignment is not a prerequisite for implementation or local checks; the actual game/release evidence requirements retain their scopes.

Service routes start with /v1/. Gateway routes use /api/{service}/...; /api/demo serves the fictional fixture and /api/status reports readiness/degradation. Every private API requires the launch session credential. Host and Origin are checked; services bind only 127.0.0.1. Internal clients disable outbound proxies and redirects; requests and timeouts are bounded. Normal logs and errors contain no credentials or private text.

The existing source-hash records verify selected static definitions only. They are not live tests of equip/unequip or reload, item ownership, legal stacking, collision or damage, or online server overrides. This stage advances M1 source mapping only; M1 online acceptance has not passed. CI results must identify their exact source commit; source changes alone do not establish a passing run or online acceptance.

Planning trials let the user enter the actual character-level start and end, or select Paragon experience and enter a separate Paragon range. The cumulative actual XP and complete elapsed time must cover exactly the same range. Comparisons pool only matching confirmed context, build, bonuses, experience kind and level range; access and character/Paragon transitions also affect whether a trial is eligible. Changing a trial input clears the displayed ranking and unchecks the consistency confirmation, so the user must review and confirm again. If trial persistence succeeds but route comparison fails, retrying the unchanged submission reuses its trial ID; changing the submitted data creates a different request identity. Rankings use total actual XP divided by total complete elapsed time. Unmeasured routes remain trial candidates. Sampling requires a defined binary event and attempt unit, complete recorded outcomes and unchanged settings; estimates include Wilson intervals and their assumptions.

New trial XP and level values are bounded at 2**53 - 1, and each rate must be finite; unusable new measurements return HTTP 400 before insertion. Historical records retain their original payload bytes and are reclassified from their inputs during retries and comparisons. Retry identity excludes derived status/unknowns; different inputs under the same ID return HTTP 409. A SQLite immediate transaction serializes the read and insert, preserving one record for concurrent identical submissions. Unsupported pooled totals become nullable, remain pending confirmation and cannot establish a best candidate. Route warnings explain excluded legacy measurements and unusable aggregates; small positive rates use scientific notation instead of appearing as zero. Storage remains version 1 without a payload migration.

Rust checks the bundle manifest before worker execution and uses a Windows Job Object for cleanup after host faults. File hashes detect corruption; a writable manifest does not authenticate its publisher. Release signing, independent dependency-rights review and clean-machine evidence remain release work. Storage v1 rejects unknown/newer versions; no migration has shipped. Offline backup/restore copies validated v1 databases and hashed BMP captures to a new destination, with an integrity manifest and instance lock. Existing targets are never overwritten. The source CLI is `python runtime.py --maintenance backup --data-dir <state> --destination <new-backup>` and `python runtime.py --maintenance restore --backup-dir <backup> --destination <new-state>`; native `--backup-to` / `--restore-from` entry wiring still needs packaged verification after rebuilding.

Acquisition cards use the API `source_id` and show their target event. Manual sample results display the returned game/version/mode/season/ruleset and content scope. Sample drafts retain count text; blank or rounded inputs cannot silently become observations. Both Planning forms share validation for nonnegative decimal integer text within the JavaScript exact-integer range. The sample API bounds counts at `2**53 - 1` and returns `invalid_sample_counts` with HTTP 400 for larger input. This follows the interoperability guidance in [RFC 8259 section 6](https://www.rfc-editor.org/rfc/rfc8259.html#section-6). Editing a sample clears its estimate and confirmations; submission disables its controls, and failure leaves no prior estimate displayed. Small nonzero interval bounds use scientific notation and near-one values remain visibly below 100%. The Wilson method, storage version and historical rules are unchanged. These checks do not accept a real-game acquisition adapter.
