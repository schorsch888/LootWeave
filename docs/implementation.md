# Implementation and validation

The implementation lives directly in the repository root. There is no enclosing application directory. The only executable pack is `synthetic-leveling` version `1.0.0`, scoped to the entirely fictional game ID `lootweave-fixture` and its Sorcerer leveling scenario. Deskrawl build 25690430 has research-only pack versions `0.1.0-research` through `0.6.0-research`; the latest adds selected original Frostwyrm code-registration tail, module-array entry and address-reference checks to the prior lifecycle evidence while leaving `rules` empty. Earlier pack bytes/hashes remain unchanged, and all six explicit versions are available through the API. These records are not accepted online-mechanics adapters. Diablo II, III and IV do not have accepted adapters.

## Boundaries

| Location | Ownership |
| --- | --- |
| frontend/src | React/TypeScript FSD: App assembles Pages, Pages compose Features and Entities, Shared provides transport and wire types |
| desktop/src | Rust/Tauri entry, Windows region capture, sessions, readiness, instance lock and descendant cleanup |
| services/profile | Unconfirmed observations and append-only confirmed snapshots; owns profile.sqlite3 |
| services/knowledge | Immutable, scoped packs and evidence; owns the pack index and content hashes |
| services/evaluation | Full-build mechanism comparison, reasons and frozen replay; owns evaluation.sqlite3 |
| services/planning | Comparable XP/time trials, source prerequisites and recorded-outcome statistics; owns planning.sqlite3 |
| services/ocr | Native Windows OCR infrastructure; owns private captures, never confirms Profile data |
| gateway.py | Authenticated UI forwarding and static assets; no game rules |
| contracts.py, transport.py, storage.py, process_lifecycle.py | Wire validation, local HTTP, SQLite and service-process lifetimes; no shared business model |

Capabilities run in separate processes and communicate through versioned HTTP APIs. Evaluation reads Profile and Knowledge, and Planning reads Knowledge. Neither opens another capability's database. The architecture check rejects upward FSD imports, feature peers, private slice imports and cross-service Python imports.

Python service runtime dependencies are standard-library modules and installed Windows APIs. Release bundles embed CPython; React, Tauri and build tools use locked dependencies. Separately runnable services and independent data ownership form the microservice boundary, while the Windows distribution packages them together.

## Development

Use Python 3.12, Node.js 24 or newer, and pnpm 11.19.0. Native capture/OCR and desktop packaging require Windows x64.

~~~powershell
pnpm --dir frontend install --frozen-lockfile
pnpm --dir frontend build
pnpm --dir frontend check:acquisition
python runtime.py
~~~

The development launcher creates a session secret, starts services on ephemeral literal-loopback addresses, waits for authenticated readiness and opens the browser. Data defaults to the ignored .local directory. Close the launcher with Ctrl+C to stop workers. Rust owns the desktop distribution's outer process scope. Before application initialization, each Windows service retains an anonymous, non-inherited kill-on-close [job object](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) for its entire process lifetime. Windows closes that handle when the service exits, reclaiming active helper descendants even during OCR startup/recognition or forced worker termination. The handle is deliberately not closed while the owner is still running.

For desktop service launches, Rust assigns its outer job before writing a one-byte boot permit to the service's existing stdin pipe. With `LOOTWEAVE_PARENT_JOB=1`, Python waits for that permit before establishing the nested service job or initializing helpers. Missing/invalid permits and ownership failures publish no readiness. The developer launcher clears the inherited desktop flag and starts independent service roots. Process cleanup is scoped to owned descendants; unrelated siblings remain running. The frozen sidecar and current Rust host must be rebuilt together before validating this protocol in a packaged application.

For desktop builds, install the Rust Windows MSVC toolchain and C++ build tools, then the pinned build dependencies:

~~~powershell
python -m pip install -r requirements-build.txt
python scripts/build_desktop.py
~~~

Use --sidecar-only to bundle Python without compiling Rust; --debug builds a debug host; --installer requests NSIS after the frontend and sidecar are built. --test-native runs release Rust tests with the same path-remapping flags as packaging. Build products are local and ignored. An installer build does not complete clean-machine acceptance.

English en-US and Simplified Chinese zh-Hans-CN OCR models are installed Windows capabilities. Text confirmation remains usable when a model or capture is unavailable. The current OCR adapter supports three generic demonstration labels: level, vitality and armor. It does not identify arbitrary affixes, icons or game layouts. Numeric parsing rejects split or incomplete digits and scientific-notation fragments, and preserves the original text, sign and unit. A readable primary recognition remains the numeric source; consistent English recognition is recorded separately as `numeric_corroboration`. `numeric_source` is reserved for cases where an unreadable number was actually recovered. The original observation and every interpreted value remain unconfirmed until the user reviews and confirms them.

Unresolved fields with a unique mapped label, explicit unit and uncontested native row geometry can request English numeric-region recognition. The worker uses the original BMP and one additional helper for at most three crops, projects word bounds back to original pixels and retains the original text/span. Readable primary values and explicit signs are preserved; conflicting candidates remain ambiguous, and consistent crops corroborate rather than replace readable values. The helper has a six-second maximum within the remaining twelve-second request budget; failure is recorded as `numeric_region_error` while primary observations remain usable. Each crop bitmap and input stream is disposed, and the helper stays in the service process scope. All values still require confirmation. The frozen current adapter's fresh synthetic v7 measurement is documented below; real-game acceptance remains open.

## Deskrawl process and window capture

The current source includes passive Deskrawl process/window detection in the Rust host. With game scope `deskrawl`, the capture feature requires explicit window selection, uses client-relative physical coordinates, and provides a three-second countdown to return manually to the game. Other scopes can retain explicit screen-region capture. The native commands are `detect_deskrawl_windows` and `capture_deskrawl_region`, each authorized by the launch session and application command permissions.

Detection reads only OS process/window metadata. It checks the executable basename and process creation identity. Minimized, hidden and unavailable windows cannot be selected; a background window can be selected, but capture requires manually bringing it to the foreground. The host verifies the same client bounds before and after the screen-region read. Multiple windows are not silently resolved. Redetection replaces session-scoped bindings. Responses are applied only when their detection generation and current context still match, so a late result cannot replace a newer window list after a scope or source change. Only game metadata is returned; full paths, PIDs, window handles and window titles are excluded. Game version and build remain unknown in the capture context.

GDI reads the selected foreground screen region inside the game client. It is not an atomic window-only capture API; overlays and changes between checks still require manual review. After capture, the UI displays the original BMP region at its native pixel dimensions and the uncorrected OCR text. The image viewer is keyboard-focusable and scrollable for larger regions. Changing game scope, capture source, selected window binding, region or language, or starting another capture clears the old image and observation association and invalidates confirmation while preserving manually entered text. Original image/text and window provenance remain unconfirmed until the separate Profile confirmation flow. A declared capture game must match the snapshot game; each new observation resets the manual checkbox.

The window source and simulated UI guards are tested. The delivered `fcc9ed1` MVP host, frozen Python and NSIS installer were built locally; its headless lifecycle and backup/restore checks pass. Later hidden/native verification uses a separate Rust-only host. Successful real-window capture, visible GUI and two-clean-machine installation/removal remain unaccepted. Run the lightweight Windows checks independently of desktop resources:

~~~powershell
cargo fetch --locked --target x86_64-pc-windows-msvc --manifest-path desktop/Cargo.toml
python scripts/check_window_guards.py
~~~

## Contracts and invariants

The original read-only [Frostwyrm evidence record](../research/deskrawl-frostwyrm.json) is checked by the default invocation, `python scripts/validate_deskrawl_frostwyrm.py`: 11 source hashes, three strict objects, two links, one managed effect, 14 layouts, two enums and nine native methods. The separate [lifecycle record](../research/deskrawl-frostwyrm-lifecycle.json) uses `python scripts/validate_deskrawl_frostwyrm.py --evidence research/deskrawl-frostwyrm-lifecycle.json` with `DESKRAWL_GAME_DIR` set to the matching installed build; it checks 12 hashes, three strict objects, two links, one managed effect, 15 layouts, two enums, 15 methods, five direct relative call/tail-jump links, one PE exception-directory function bound (see [Microsoft’s x64 exception-handling explanation](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64)) and one previous-record hash/scope link. Both read-only checks were repeated against build 25690430 and report `online_validated=false` and `m1_accepted=false`. The selected rebuild trace shows an equipment deflection count and target mode reset before later effect callbacks, plus a separate count-pool reset. Tests reject incorrect relative-link opcodes/targets/ranges, duplicate edges, ambiguous exception bounds and tampered prior evidence. This does not cover all equip/unequip events, virtual slot mapping, duplicates/stacking, ownership or online behavior, and does not establish complete lifecycle acceptance.

The separate [method-slot record](../research/deskrawl-frostwyrm-method-slots.json) adds original metadata v39 checks for two types, four method declarations and two concrete method-index targets. The new `0.4.0-research` pack has empty `rules`, and the earlier explicit research versions remain available. Only the recorded index-width/stride profile is supported; different profiles and false claims fail. Declaring types and metadata slots 4/5 are verified for the selected methods. Native class vtable layout, pointer materialization, runtime dispatch and live equip/unequip behavior remain unaccepted; see the [research reproduction steps](research.md).

The separate [module-pointer record](../research/deskrawl-frostwyrm-module-pointers.json) links the original metadata image to two token-indexed entries in a matching x64 module prefix. Both pointers match the previously hashed concrete method bodies. The `0.5.0-research` pack adds this evidence with empty `rules`; historical research versions remain explicit and unchanged historical versions remain available. This does not verify the runtime registration root, class-vtable materialization, indirect dispatch or live events. The checker uses only existing standard-library PE/metadata readers and introduces no runtime or storage change.

The separate [code-registration record](../research/deskrawl-frostwyrm-code-registration.json) adds a hashed 136-byte x64 v39 registration structure, its 95-entry module-array range and selected Assembly-CSharp entry, plus a RIP-relative address reference in a second PE exception-bounded body. Native module index 6 differs from metadata image index 3; the checker binds them by the actual pointer. The `0.6.0-research` pack keeps rules empty, all six research versions explicit and previous bytes unchanged. Execution of registration, other fields/modules, class-vtable materialization, generic/adjustor paths and gameplay dispatch remain unaccepted. Per user direction, named-owner/reviewer assignment is not a prerequisite for implementation or local checks; the actual game/release evidence requirements retain their scopes.

Service routes start with /v1/. Gateway routes use /api/{service}/...; /api/demo serves the fictional fixture and /api/status reports readiness/degradation. Every private API requires the launch session credential. Host and Origin are checked; services bind only 127.0.0.1. Internal clients disable outbound proxies and redirects; requests and timeouts are bounded. Normal logs and errors contain no credentials or private text.

| Capability | Main routes |
| --- | --- |
| Profile | POST /v1/observations; POST /v1/confirmations; GET /v1/profiles/{id}/revisions/{revision}; POST /v1/snapshots/validate |
| Knowledge | GET /v1/packs; GET /v1/packs/{id}/{version} |
| Evaluation | POST /v1/evaluations; GET /v1/evaluations/{id}; POST /v1/evaluations/{id}/replay |
| Planning | POST /v1/trials; POST /v1/routes/compare; POST /v1/sources/eligibility; POST /v1/drop-estimates |
| OCR | GET /v1/health; POST /v1/regions |

Observations stay unconfirmed and immutable. Confirmation is explicit, idempotent by request hash and uses an expected revision inside a write transaction. Items are actual instances with finite rolls, units and evidence. Incomplete inventory, unknown conditions, version conflicts and inconsistent capture times block a definitive conclusion.

Replacement removes the equipped instance, inserts the candidate and recomputes the complete build: skills, actor ownership, equipment/rune set thresholds, resource and survival capabilities. Panel observations are not added to their sources. Rank-zero skills and inactive conditions do not activate effects. Retention and equip eligibility are separate; future combinations require explicit allowed changes and retain feasibility uncertainty.

Snapshot confirmation returns a `build_hash` for the actual equipped build. Its fingerprint excludes capture time, evidence and an unequipped candidate; changing actual build contents changes the fingerprint. Evaluation results pin Profile revision/facts hash, pack version/hash, intent and evaluator version. `GET /v1/evaluations` returns the latest 100 frozen evaluations, each with its evaluation ID, retention and pin. Frozen inputs and result hashes allow replay with source services offline. A missing historical engine is reported, rather than silently reinterpreting its results. This engine compares capabilities without calculating DPS, affix weights or improvement percentages.

Current evaluations pin engine `0.1.5`. It retains the three-state capability handling introduced in `0.1.4` and adds same-slot actual affix differences for matching identifiers and units; missing values remain absent, and differences do not establish DPS or an improvement. Capability state is aggregated by actor/capability: any active provider yields active; with none active, any unknown provider yields unknown; otherwise the state is inactive. Definite losses require active-to-inactive and gains require inactive-to-active. Required capabilities with unknown state are excluded from known-missing rows. The additive `comparison.uncertain_mechanisms` lists affected actors, capabilities and before/after states; the frontend shows these as pending confirmation. Original per-rule and input provenance remains in the resolved rows, and unknown rule blockers remain even when another provider establishes the capability. Required capabilities absent from the compatible knowledge pack still produce `unknown_required_capability`; incompatible context, class, content, execution policy or scenario prevents rule resolution and comparison. Actor-specific skill/set requirements and the hero default for unspecified embedded actors remain unchanged. Historical results without the additive fields retain their original presentation.

Historical engines `0.1.0` through `0.1.4` remain available through explicit pinned replay, preserving original behavior and hashes. A new request ID creates a corrected evaluation; reusing a historical request returns its stored result. Four [0.1.0 cases](../fixtures/evaluation-0.1.0.json), six [0.1.1 cases](../fixtures/evaluation-0.1.1.json), six [0.1.2 cases](../fixtures/evaluation-0.1.2.json) and eight [0.1.3 cases](../fixtures/evaluation-0.1.3.json) replay ten times each with source services unavailable. The new eight cases were frozen before the fix and include unknown transitions, companion ownership, an active alternative provider and known loss/gain controls. An explicit nine-entry provider-state oracle checks 162 validated fictional combinations; all current summaries match, and all original 0.1.3 hashes replay exactly. Actual HTTP regressions preserve provenance and verify ten offline replays. Storage remains v1; no data migration is required.

Planning trials let the user enter the actual character-level start and end, or select Paragon experience and enter a separate Paragon range. The cumulative actual XP and complete elapsed time must cover exactly the same range. Comparisons pool only matching confirmed context, build, bonuses, experience kind and level range; access and character/Paragon transitions also affect whether a trial is eligible. Changing a trial input clears the displayed ranking and unchecks the consistency confirmation, so the user must review and confirm again. If trial persistence succeeds but route comparison fails, retrying the unchanged submission reuses its trial ID; changing the submitted data creates a different request identity. Rankings use total actual XP divided by total complete elapsed time. Unmeasured routes remain trial candidates. Sampling requires a defined binary event and attempt unit, complete recorded outcomes and unchanged settings; estimates include Wilson intervals and their assumptions.

New trial XP and level values are bounded at 2**53 - 1, and each rate must be finite; unusable new measurements return HTTP 400 before insertion. Historical records retain their original payload bytes and are reclassified from their inputs during retries and comparisons. Retry identity excludes derived status/unknowns; different inputs under the same ID return HTTP 409. A SQLite immediate transaction serializes the read and insert, preserving one record for concurrent identical submissions. Unsupported pooled totals become nullable, remain pending confirmation and cannot establish a best candidate. Route warnings explain excluded legacy measurements and unusable aggregates; small positive rates use scientific notation instead of appearing as zero. Storage remains version 1 without a payload migration.

Rust checks the bundle manifest before worker execution and uses a Windows Job Object for cleanup after host faults. File hashes detect corruption; a writable manifest does not authenticate its publisher. Release signing, independent dependency-rights review and clean-machine evidence remain release work. Storage v1 rejects unknown/newer versions; no migration has shipped. Offline backup/restore copies validated v1 databases and hashed BMP captures to a new destination, with an integrity manifest and instance lock. Existing targets are never overwritten. The source CLI is `python runtime.py --maintenance backup --data-dir <state> --destination <new-backup>` and `python runtime.py --maintenance restore --backup-dir <backup> --destination <new-state>`; native `--backup-to` / `--restore-from` entry wiring still needs packaged verification after rebuilding.

Acquisition cards use the API `source_id` and show their target event. Manual sample results display the returned game/version/mode/season/ruleset and content scope. Sample drafts retain count text; blank or rounded inputs cannot silently become observations. Both Planning forms share validation for nonnegative decimal integer text within the JavaScript exact-integer range. The sample API bounds counts at `2**53 - 1` and returns `invalid_sample_counts` with HTTP 400 for larger input. This follows the interoperability guidance in [RFC 8259 section 6](https://www.rfc-editor.org/rfc/rfc8259.html#section-6). Editing a sample clears its estimate and confirmations; submission disables its controls, and failure leaves no prior estimate displayed. Small nonzero interval bounds use scientific notation and near-one values remain visibly below 100%. The Wilson method, storage version and historical rules are unchanged. These checks do not accept a real-game acquisition adapter.

Separate label/value lines are associated only when valid native bounds place the value to the right on the same row, both sides have one matching candidate, and no competing native text or duplicate label is present. The value keeps its original `raw_text`/`span`; `label_source` separately retains the label's text, span and bounds. Invalid or Boolean bounds cannot support association. A label-only level may use a standalone English number to its right only with the same row and exclusivity checks. Explicit units, primary signs and reader conflicts retain their existing rules; all observations require confirmation. Unmappable native lines are skipped and prevent new split-row associations.
